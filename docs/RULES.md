# Verilinter Rule Catalog

This file is the current inventory of implemented lint rules and the cases they cover.

## Rule Template

Use this template when adding a new rule entry:

Rendered example:

| Rule | Code | Language Scope | Match Level | Covers | Implemented By | Tests | Known Limitations |
|---|---|---|---|---|---|---|---|
| Short rule name | `RULE_CODE` | `Verilog`, `SystemVerilog`, or `Both` | `token`, `node`, or `block` | One-sentence description of the cases the rule flags. | `src/pkg/rules/.../rule_file.py` | `tests/.../test_file.py` | Any important gaps, heuristics, or current behavior quirks. |

Copy/paste template:

```md
| Rule | Code | Language Scope | Match Level | Covers | Implemented By | Tests | Known Limitations |
|---|---|---|---|---|---|---|---|
| Short rule name | `RULE_CODE` | `Verilog`, `SystemVerilog`, or `Both` | `token`, `node`, or `block` | One-sentence description of the cases the rule flags. | `src/pkg/rules/.../rule_file.py` | `tests/.../test_file.py` | Any important gaps, heuristics, or current behavior quirks. |
```

Guidelines:

- Keep `Covers` tied to what the current implementation actually does, not what we intend it to do later.
- `Language Scope` means the language family the current rule meaningfully applies to:
  `Verilog`, `SystemVerilog`, or `Both`.
- `Match Level` means what kind of vnode the rule anchors its diagnostic to:
  `token` for a punctuation/keyword token, `node` for a syntax node, `block` for a whole procedural or structural construct.
- Use repo-relative paths in `Implemented By` and `Tests`.
- If a rule has no meaningful current limitation, write `None noted`.
- If a rule does not yet define a dedicated diagnostic code, say so explicitly instead of inventing one here.
- For contributor-facing wording, "simulation / SystemVerilog-specific declaration forms" means constructs that are common in verification, testbench, or richer SystemVerilog structural modeling and are outside this project's restricted RTL subset. That category includes `program`, `clocking`, `checker`, `interface`, `modport`, and `package` declarations. These may appear around a DUT, but they are not limited to test files.
- There are two useful mental buckets for syntax-policy rules:
  classic synthesizable-RTL exclusions are constructs that strict RTL codebases usually ban because they are legacy, non-synthesizable, or easy to misuse in hardware design;
  SystemVerilog verification-oriented structure rules are constructs that are valid SystemVerilog but are intentionally excluded because this project wants a smaller RTL-focused subset rather than the full language.

## Width and Signedness

Rules in `src/pkg/rules/width_and_signedness/`.

| Rule | Code | Language Scope | Match Level | Covers | Implemented By | Tests | Known Limitations |
|---|---|---|---|---|---|---|---|
| Unsized decimal literal | `NO_UNSIZED_LITERAL` | `Both` | `node` | Flags a plain, unsized, unbased decimal literal (`5`) used as the direct right-hand side of a blocking, non-blocking, or continuous assignment; its width will be inferred from context and may silently mismatch the target signal's declared width. | `src/pkg/rules/width_and_signedness/no_unsized_literal.py` | `tests/rules/width_and_signedness/test_no_unsized_literal.py`, `tests/test_run_lint.py`, `tests/test_rule_registration.py` | First pass only covers the two simple assignment kinds (`=`, `<=`); compound assignments (`x += 5;`) are intentionally out of scope. A classic procedural `for (i = 0; ...; i = i + 1)` loop header is explicitly excluded (its init/step clauses parse as ordinary assignment nodes parented by `ForLoopStatementSyntax`, the same shape as an ordinary assignment); a `generate for` header needs no such exclusion since `LoopGenerateSyntax` models its init/step via dedicated fields rather than a nested assignment expression. `8'd5`/`'hFF`-style sized or based literals (`IntegerVectorExpression`) and `'0`/`'1`/`'x`/`'z` (`UnbasedUnsizedLiteralExpression`) are different pyslang `SyntaxKind`s entirely and are unaffected. |
| Assignment width mismatch | `ASSIGNMENT_WIDTH_MISMATCH` | `Both` | `node` | Flags an assignment target (simple identifier or sliced/indexed array element) whose effective width differs from a right-hand side whose width is independently recoverable (a plain identifier, sized literal, part/bit-select, shift operation, or concatenation of the same), or an array element bit-select whose index selector width is narrower than required to address the dimension. In-module sibling of `PORT_CONNECTION_WIDTH_MISMATCH`, which covers the same shape at instance-port boundaries instead. | `src/pkg/rules/width_and_signedness/no_assignment_width_mismatch.py` | `tests/rules/width_and_signedness/test_no_assignment_width_mismatch.py`, `tests/rules/width_and_signedness/test_nested_scope_width_regressions.py` | Reuses `simple_expression_width_and_signed` (also used by `PORT_CONNECTION_WIDTH_MISMATCH`); only fires when both sides' widths are independently known, so an unsized-literal RHS at the *top level* (`NO_UNSIZED_LITERAL`'s concern) or any richer expression (arithmetic, reduction, ternary) is silently skipped rather than guessed at. Supports simple identifier targets as well as indexed and sliced array targets (via `AssignmentTarget`, `Symbol.packed_dimension_widths`, and `Symbol.unpacked_dimension_widths`); concatenated targets remain out of scope, same posture as `NO_SELF_ASSIGNMENT`. Declarations with parameterized packed dimensions (`wire [WIDTH-1:0] sig;`) and RHS slice/replication expressions evaluate parameters via constant folding in the module scope. Accurately resolves unpacked array element accesses (`mem[i]`, `imd_val_q_i[1]`, sliced elements `mem[i][7:0]`, and multidimensional unpacked arrays) without collapsing sliced targets to base symbol widths. Differentiates scalar declarators from bracketed comment trivia. Validates array index selectors against required index widths ($\lceil \log_2(\text{dimension\_size}) \rceil$), detecting width expansion and truncation mismatches on array bit extraction. `declarator_bit_width`/`declarator_is_signed` (`src/pkg/parser/_syntax_queries/shapes.py`) recognize both `DataDeclarationSyntax` (`reg`/`logic`/plain variable declarations) and `NetDeclarationSyntax` (`wire [N:0] sig;`) ancestors. A bare unsized literal used as *one member of a concatenation* (`{a, 5}`) is fixed by IEEE 1800 at exactly 32 bits, unlike a top-level unsized right-hand side whose width is context-determined and unrecoverable; `_concatenation_member_width` (`src/pkg/parser/_syntax_queries/access.py`) applies that sizing to a concatenation or replication member, so `wire [7:0] x; assign x = {a, 5};` reports its mismatch. |
| Assignment signedness mismatch | `ASSIGNMENT_SIGNEDNESS_MISMATCH` | `Both` | `node` | Signedness sibling of `ASSIGNMENT_WIDTH_MISMATCH`: flags a simple identifier assignment target whose declared signedness differs from a right-hand side whose signedness is independently recoverable. | `src/pkg/rules/width_and_signedness/no_assignment_width_mismatch.py` | `tests/rules/width_and_signedness/test_no_assignment_width_mismatch.py` | Same recoverability and LHS-shape limits as `ASSIGNMENT_WIDTH_MISMATCH`; the two share one file and one underlying helper pair since both read the same LHS symbol and the same `simple_expression_width_and_signed` call, mirroring how `PORT_CONNECTION_WIDTH_MISMATCH`/`PORT_CONNECTION_SIGNEDNESS_MISMATCH` already share `port_connection_width_mismatch.py`. |
| Sized literal width overflow | `LITERAL_WIDTH_OVERFLOW` | `Both` | `node` | Flags a fully-numeric, unsigned sized literal (`4'hFF`) whose value needs more bits than its declared width. | `src/pkg/rules/width_and_signedness/literal_width_overflow.py` | `tests/rules/width_and_signedness/test_literal_width_overflow.py` | Kind-based check over `SyntaxKind.IntegerVectorExpression` (`INTEGER_VECTOR_EXPRESSION_KIND`), reading the node's `.size`/`.base`/`.value` tokens directly. First pass only covers unsigned literals -- a signed literal's (`4'shF`) two's-complement minimum-width math is a separate, more careful calculation not attempted here -- and skips any value containing `x`/`z`/`?` digits, since a partially-unknown value has no single well-defined minimum width. |
| Explicit X/Z literal | `EXPLICIT_XZ_LITERAL` | `Both` | `node` | Flags an explicit `'x`/`'z` unbased-unsized literal, or a sized literal (`4'bx01z`) whose value contains an `x`/`z`/`?` bit, used directly as a value in RTL -- an X/Z-containing value is not a value that can ever appear on synthesized hardware and defeats reset/comparison determinism. | `src/pkg/rules/width_and_signedness/explicit_xz_literal.py` | `tests/rules/width_and_signedness/test_explicit_xz_literal.py` | Reads `UnbasedUnsizedLiteralExpression.literal` and `IntegerVectorExpression.value` directly, the same two `SyntaxKind`s `LITERAL_WIDTH_OVERFLOW` already reads -- the two rules never double-fire since `sized_literal_overflow` already excludes any value containing `x`/`z`/`?`. | Port connection width mismatch | `PORT_CONNECTION_WIDTH_MISMATCH` | `Both` | | Flags instance connections where a known child-port width differs from a known connected-expression width. | `src/pkg/rules/width_and_signedness/port_connection_width_mismatch.py` | `tests/rules/width_and_signedness/test_port_connection_width_mismatch.py`, `tests/test_run_lint.py` | Evaluates packed integer ranges on declarations and simple identifier, slice, replication, or sized-literal connection expressions. | Port connection signedness mismatch | `PORT_CONNECTION_SIGNEDNESS_MISMATCH` | `Both` | | Flags instance connections where a known child-port signedness differs from a known connected-expression signedness. | `src/pkg/rules/width_and_signedness/port_connection_width_mismatch.py` | `tests/test_run_lint.py` | Same first-pass limitation profile as `PORT_CONNECTION_WIDTH_MISMATCH`: it only fires when both sides have directly recoverable signedness metadata from simple declarations or sized literals. |
| Assignment truncation | `ASSIGNMENT_TRUNCATION` | `Both` | `node` | Narrower, direction-specific sibling of `ASSIGNMENT_WIDTH_MISMATCH`: flags only the lossy direction, where the right-hand side's recoverable width is strictly wider than the target's declared width. | `src/pkg/rules/width_and_signedness/no_assignment_width_mismatch.py` | `tests/rules/width_and_signedness/test_no_assignment_width_mismatch.py`, `tests/rules/width_and_signedness/test_nested_scope_width_regressions.py`, `tests/test_rule_overlap_harness.py` | Always co-fires with `ASSIGNMENT_WIDTH_MISMATCH` on the same construct (declared via `overlaps_with`) -- a safe narrower-to-wider (zero/sign-extending) assignment is `ASSIGNMENT_WIDTH_MISMATCH`'s concern only, not this rule's. | Shift amount out of range | `SHIFT_AMOUNT_OUT_OF_RANGE` | `Both` | `node` | Flags a shift expression (`<<`, `>>`, `<<<`, `>>>`) whose constant shift amount is negative or `>=` the shifted operand's recoverable width (supports identifiers, bit/part-selects, concatenations, and nested shifts via `simple_expression_width_and_signed`). | `src/pkg/rules/width_and_signedness/shift_amount_out_of_range.py` | `tests/rules/width_and_signedness/test_shift_amount_out_of_range.py` | Only fires when the shifted operand's width is recoverable via `simple_expression_width_and_signed` and the shift amount is a compile-time constant expression (`evaluate_constant_expression` with scope parameter lookup); an unresolvable shifted operand or variable shift amount is silently skipped rather than guessed at. |
| Arithmetic result truncation | `ARITHMETIC_RESULT_TRUNCATION` | `Both` | `node` | Flags a simple identifier assignment target or declarator initializer whose declared width is narrower than the natural (self-determined) result width of a direct `+`/`-`/`*` right-hand side (`max` of operand widths for add/subtract, sum of operand widths for multiply) -- e.g. `wire [7:0] p; assign p = a * b;` or `wire [7:0] p = a * b;` with 8-bit `a`/`b` silently drops the true 16-bit product's high bits. | `src/pkg/rules/width_and_signedness/arithmetic_result_truncation.py` | `tests/rules/width_and_signedness/test_arithmetic_result_truncation.py`, `tests/rules/width_and_signedness/test_nested_scope_width_regressions.py` | Only fires when both operands' widths are independently recoverable via `simple_expression_width_and_signed`; supports parameterized operand and target declarations (`[WIDTH-1:0]`) resolved via module scope parameters. ## Notes

- The README gives a short feature summary; this file is the more complete rule inventory.
- If a new rule is added, update this file in the same change so the rule list stays accurate.
- Rule-shape policy: prefer precise construct rules first (`NO_IF_GENERATE`, `NO_GENERATE_FOR`, `NO_CASE_GENERATE`) and add broad umbrella rules only when overlap is an explicit policy goal. In other words, avoid adding a catch-all rule like `NO_GENERATE_REGION` unless we intentionally want both the broad policy diagnostic and the more specific construct diagnostic to fire together.
